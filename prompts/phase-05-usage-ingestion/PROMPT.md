# Objective

Implement the high-throughput Usage Event ingestion system required by the assignment.

The assignment specifically requires:

- POST /usage
- high-throughput usage recording
- idempotent retries
- usage events recorded per customer per day
- high write volume
- basic rate limiting
- architecture capable of handling 50L+ usage-event rows
- queued aggregation in a later phase

This phase is ONLY responsible for reliable ingestion and persistence of raw usage events.

Daily aggregation will be implemented in Phase 6.

# 1. Core Domain

The relationship is:

Merchant
  ↓
Customer
  ↓
Subscription
  ↓
Usage Events

A usage event represents usage generated by a customer.

The event must be associated with:

- merchant
- customer
- subscription
- event identifier
- usage quantity
- occurrence timestamp

The raw usage event is the source of truth.

Do NOT store only aggregated usage.

---

# 2. Usage Event Schema

Create a `usage_events` table.

At minimum:

- id
- public_id
- merchant_id
- customer_id
- subscription_id
- event_id
- quantity
- occurred_at
- created_at

Consider whether an event type/category is useful, but do not introduce unnecessary dimensions unless justified.

The assignment describes usage as units consumed by a customer.

Keep the schema simple.

---

# 3. Event ID / Idempotency

This is a critical requirement.

The client must provide a unique `event_id`.

Example:

POST /api/v1/usage

{
  "event_id": "evt_01ABC...",
  "customer_id": "customer-public-id",
  "quantity": 25,
  "occurred_at": "2026-09-29T14:30:00Z"
}

Create a database uniqueness constraint:

UNIQUE(merchant_id, event_id)

This ensures retries do not create duplicate usage.

IMPORTANT:

Do NOT rely only on:

if exists then insert

because concurrent requests can race.

The database uniqueness constraint must be the final authority.

---

# 4. Idempotent Retry Behavior

If the same:

merchant_id + event_id

is submitted again:

- Do not create another event.
- Do not increment anything.
- Do not enqueue duplicate aggregation work unnecessarily.
- Return a deterministic successful response indicating the event already exists.

The API should be safe for clients to retry after:

- network timeout
- connection reset
- client timeout
- temporary server error

Document the idempotency behavior.

---

# 5. Event ID Rules

Validate:

- required
- string
- reasonable maximum length
- non-empty
- client-generated

Do not use the database auto-increment ID as the idempotency key.

The event ID belongs to the merchant/client domain.

---

# 6. Customer Validation

The customer must:

- belong to the authenticated merchant
- exist
- be active

Never accept an arbitrary cross-tenant customer.

Do not trust:

merchant_id

from the request.

Merchant must come from:

MerchantContext.

---

# 7. Subscription Validation

The usage event must reference a valid subscription.

Verify:

- subscription belongs to authenticated merchant
- subscription belongs to the supplied customer
- subscription is active
- subscription is valid for the event timestamp where appropriate

IMPORTANT:

Think carefully about historical usage.

Usage may arrive late.

For example:

Subscription:

Plan A
Jan 1 → Jan 15

Plan B
Jan 15 → Jan 31

Usage:

occurred_at = Jan 10

The event must retain the original occurrence timestamp.

Do NOT simply use the current subscription plan.

Do not calculate billing in this phase.

The event only records the raw fact of usage.

Document the assumption.

---

# 8. Quantity

Validate:

- required
- integer
- positive
- reasonable upper bound

Do not use floating-point quantities unless the assignment explicitly requires fractional usage.

The assignment describes usage in units.

Use an integer representation.

Document the decision.

---

# 9. occurred_at

The client must provide:

occurred_at

Store timestamps in UTC.

Accept ISO-8601 timestamps.

Normalize the stored timestamp to UTC.

Do not use application-local time for persistence.

The occurrence timestamp determines the usage date and later aggregation period.

---

# 10. Late Events

Usage events can arrive late.

Example:

Current date:

2026-09-29

Client submits:

occurred_at = 2026-09-27

The event should still be accepted if it satisfies the business validation rules.

Do NOT reject valid late events merely because their timestamp is older than the current date.

The later aggregation phase must be capable of recomputing affected daily totals.

Document this design.

---

# 11. Future-Dated Events

Decide how future timestamps should behave.

For this assignment, reject events that are unreasonably far in the future.

A small clock-skew tolerance may be allowed.

Document the chosen boundary.

Do not over-engineer time validation.

---

# 12. High-Throughput Write Path

This endpoint is expected to receive high write volume.

The request path must be lightweight.

Recommended flow:

Request
  ↓
Authentication
  ↓
Rate limiting
  ↓
Validation
  ↓
Tenant/customer/subscription validation
  ↓
Insert raw usage event
  ↓
Return success
  ↓
Async aggregation boundary

Do NOT perform expensive aggregation synchronously.

Do NOT calculate:

- daily totals
- monthly totals
- invoices
- overage

inside the request.

---

# 13. Queue Boundary

After successful insertion, establish the asynchronous aggregation boundary if appropriate.

For example:

UsageEventRecorded
    ↓
Queue
    ↓
Future DailyUsage aggregation

However:

Do not implement the actual aggregation logic in this phase.

The purpose is to ensure the ingestion architecture can later hand work to the queue without coupling aggregation to the HTTP request.

If dispatching an event/job, make sure duplicate retries do not create unnecessary duplicate work.

Document the choice.

---

# 14. Database Transactions

Keep the ingestion transaction minimal.

The core requirement is:

Raw usage event must be durably stored.

Avoid wrapping unnecessary external/slow operations inside the database transaction.

If an event is inserted successfully, it must remain the source of truth even if later asynchronous processing fails.

---

# 15. Database Indexing

This table can eventually contain 50L+ rows.

Think carefully about indexes.

Required/important indexes should include:

- unique(merchant_id, event_id)
- merchant_id + occurred_at
- customer_id + occurred_at
- subscription_id + occurred_at

Only add indexes justified by actual access patterns.

IMPORTANT:

Every additional index increases write cost.

Document the trade-off between:

- ingestion write performance
- lookup/query performance

---

# 16. 50L+ Rows Strategy

The assignment explicitly asks you to explain how the system handles 50L+ usage-event rows.

3. Use queued asynchronous aggregation.
4. Keep daily aggregates in a separate read model in Phase 6.
5. Avoid querying raw events for every dashboard request.
6. Consider date-based partitioning as a scale option.
7. Document when partitioning would become appropriate.

    ↓

Explain that raw events remain the source of truth.

Do not claim the current implementation has solved arbitrary scale.

Clearly distinguish current implementation from future scaling options.
